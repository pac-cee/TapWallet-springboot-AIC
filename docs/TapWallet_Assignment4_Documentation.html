1. Introduction

TapWallet is a digital wallet for Rwanda: customers keep a balance in a wallet, top it up, and pay registered merchant shops; administrators manage users and shops. Assignment 3 delivered the domain model and a JSF interface. This assignment re-implements the persistence and business layer as a Spring Boot REST application with no frontend: every operation is exposed as a JSON endpoint and exercised with Postman.

The three entities selected for full CRUD are User, Wallet and Merchant. A fourth entity, Payment, is included because it is what makes the business rules meaningful: a payment moves money between a wallet and a merchant in one transaction. A payment is a historical record, so it can be created, read and reversed but never edited or deleted.

4. REST endpoints

Base URL: http://localhost:8080. All bodies are JSON. Create returns 201, delete returns 204, everything else 200.

5. Business rules implemented

Rules are enforced in the service layer and reported with a consistent status code. Input-shape rules (required fields, formats, ranges) are enforced earlier by Bean Validation on the DTOs.

UserEmail is unique (case-insensitive) and phone is unique409

UserCannot be deleted while owning a wallet or operating a shop422

WalletNo overdraft: a withdrawal or payment cannot exceed the balance422
WalletA FROZEN wallet, or a wallet whose owner is frozen, cannot transact422

6. Running the application

  1. Requirements: JDK 17 and Maven 3.
  2. Unzip the project and run mvn spring-boot:run in its folder (or open it in IntelliJ / VS Code and run TapWalletApplication).
  3. The API listens on http://localhost:8080. The in-memory H2 database is created and seeded on every start; the H2 console is at http://localhost:8080/h2-console (JDBC URL jdbc:h2:mem:tapwallet, user sa, no password).
  4. Run mvn test to execute the 20 automated MockMvc tests.

7. Testing with Postman

  1. Open Postman → Import → choose postman/TapWallet.postman_collection.json.
  2. The collection variable baseUrl is already http://localhost:8080.
  3. Run the four folders in order: 1. Users → 2. Wallets → 3. Merchants → 4. Payments. Each create request has a test script that saves the returned id into a collection variable (userId, merchantUserId, walletId, merchantId, paymentId) so later requests reference it automatically.
  4. Requests prefixed [Rule] deliberately break a business rule and assert the expected error status (400, 404, 409 or 422).
  5. Use the Collection Runner to execute a whole folder and see every assertion pass in one view.
The collection contains 54 requests: 12 for Users, 17 for Wallets, 12 for Merchants and 13 for the payment flow. Every request carries a pm.test assertion on the status code.

Suggested demo walkthrough (for the video)

  1. Start the app, show the seeded users in GET /api/users.
  2. Users: create Grace (customer) and the bakery owner (merchant) — then show a 400 validation error and a 409 duplicate email.
  3. Wallets: open Grace's wallet, top up, withdraw, then try an overdraft (422) and a second wallet for Alice (409).
  4. Merchants: register the bakery, update it, freeze/activate; show the bad code format (400) and Alice as operator (422).
  5. Payments: Alice pays Kigali Cafe 1 500 RWF — point out the wallet balance going down and the merchant revenue going up in the same response. Reverse it and show both restored. Reverse again → 422.
  6. Open the H2 console to show the tables and the foreign keys between them.

8. Automated tests

Twenty @SpringBootTest + MockMvc tests (five per controller) cover the create-read-update-delete cycle of each entity and every business rule listed above, including the money movement and reversal of a payment. They run with mvn test and all pass.
